II. Variantes: Lite vs Complet

Un seul repo, deux chemins via feature flags dans config.toml.

Feature v1 Complet v1 Lite Rationale
WebAuthn ✅ Full FIDO2 ✅ Full FIDO2 Core, non-negotiable
TOTP/HOTP ✅ Both ✅ TOTP only (basic) Lite: simplify anti-replay
Recovery codes ✅ 16x codes ✅ 8x codes Lite: fewer edge cases
Admin RBAC ✅ 3 roles ❌ Solo only Lite: one admin assumption
Dual-approval ✅ Included ❌ Skip Lite: no governance needed
GDPR 30-day ✅ Included ❌ Immediate delete Lite: no legal requirement
Postgres ✅ Supported ❌ SQLite only Lite: no HA needed
KEK rotation ✅ Automated jobs ❌ Static key (manual rotate later) Lite: ops simplicity
Effort 13–14 weeks 3–4 weeks (73% reduction) 73% effort savings

Decision for Will: Launch with Lite (3–4 weeks), graduate to Complet features as customers demand them. No re-architecture needed.

III. Spécification technique (résumé)

Stack

  • Backend: Go 1.22+, mono-binary
  • Database: SQLite (Lite), Postgres (Complet)
  • Crypto: AES-256-GCM only (FIPS-ready)
  • API: HTTP/JSON, OpenAPI 3.1
  • Deployment: Docker, systemd, on-premise
  • Admin UI: React, single-page app (minimal JS bundle)

Core APIs

POST /v1/webauthn/{subject}/register POST /v1/webauthn/{subject}/register/complete POST /v1/webauthn/{subject}/assert POST /v1/webauthn/{subject}/assert/complete POST /v1/totp/{subject}/verify POST /v1/recovery/{subject}/consume GET /v1/health POST /admin/v1/subjects/{id}/credentials/{cid}/revoke (admin:full) POST /admin/v1/subjects/{id}/throttle/reset (admin:operator) GET /admin/v1/audit?event_type=...&limit=100

Security angles (v1 mitigations)

  • KEK loss → versioning + file backup
  • DB corruption → SQLite WAL + hourly snapshots
  • Admin abuse → dual-approval (Complet only) + immutable audit log
  • Device compromise → counter monotonicity + device binding
  • TOTP replay → CAS (Compare-And-Swap) + backoff
  • Cross-tenant (SaaS) → tenant_id everywhere, RLS phase 6

IV. Development Considerations

Testing strategy

Level Scope Coverage target
Unit tests Crypto (envelope, KEK), TOTP/HOTP, counter logic 90%+
Integration tests API endpoints, DB schema, RBAC enforcement 80%+
Security tests Attestation validation (mock certs), device binding, replay protection 100%
Performance tests WebAuthn verify <100ms, TOTP verify <50ms Baseline
Conformance tests WebAuthn L2 spec compliance, TOTP RFC 6238 Full
Fuzz tests Attestation parsing, recovery code format Continuous

Code quality gates (before merge)

  • No secrets in code (gitleaks check)
  • Linting (golangci-lint)
  • Type safety (Go compiler)
  • Security (gosec)
  • Coverage >80% (codecov)
  • No panics in prod code (allowed only in init/main)

Crypto review checkpoints

⚠️ CRITICAL: Cryptographic operations must be reviewed by someone who's done this before.
  • Envelope format (nonce || ciphertext || tag) ← review before phase 1 lock
  • KEK derivation & versioning ← security audit
  • Device binding hash (what goes into hash?) ← threat model review
  • Counter jump detection thresholds (10 vs 100) ← fuzz testing

Recommendation: Get one security review before shipping (phase 1.5 → phase 2).

Database compatibility testing

  • SQLite 3.35+ (for JSON1 extension, WAL)
  • Postgres 12+ (for JSON, RLS)
  • Both in CI (parallel pipelines)
  • Migration scripts tested on both

Known complexity areas (high risk)

WebAuthn attestation cert validation

Certificate chain validation is complex (root chains, CRL, OCSP). Plan 3–5 days for debugging cert issues across vendors (Apple, Google, Yubico, Microsoft).

Desktop platform interop

Windows Hello, macOS Face ID, Linux FIDO2 behave differently. Test on all three platforms early. Plan 2–3 days for quirks.

TOTP anti-replay (CAS)

Race condition if two auth attempts hit DB simultaneously. Must use DB-level CAS (SQLite: UPDATE WHERE, Postgres: RETURNING).

Device binding anomaly detection

Deciding when a "device change" is suspicious vs normal (cert rotate, new Yubikey). Threshold tuning (counter jump 10 vs 100) is empirical.

Admin dashboard complexity creep

Keep admin UI minimal (3 clicks max). Resist urge to add "advanced settings" tabs. Write mockups first, freeze scope.

Audit log immutability enforcement

DB triggers prevent UPDATE/DELETE on audit_log. Test this rigorously (attacker won't be nice to you).

Tech debt to avoid

  • ❌ Plaintext secrets in config (use env vars only)
  • ❌ Global state for crypto operations (use context + dependency injection)
  • ❌ Error messages leaking info (log internally, return generic HTTP 400 externally)
  • ❌ Admin operations without audit logging (every admin action = audit entry)
  • ❌ Skipping RBAC enforcement for "just this one endpoint" (slippery slope)
  • ❌ Hard-coded thresholds (all config = flags + env vars)

VI. Anticipations & Risk Mitigation

Risk: Installation fails for user

What could go wrong?

User runs docker-compose up, gets error. No support email exists.

Mitigation
  • Pre-flight check script (validate Docker, disk space, ports)
  • Error messages are plain English (not Go stack traces)
  • TROUBLESHOOT.md covers 95% of install issues (permission, port, disk)
  • docker-compose.yml is pre-tested on Linux, Mac, Windows

Risk: Customer "hits a bug"

What could go wrong?

Customer's auth fails. They open a GitHub issue. Will must respond fast.

Mitigation
  • Extensive logging (all auth attempts logged, searchable)
  • Health endpoint + metrics show root cause (DB down? KEK missing?)
  • Recovery procedure in TROUBLESHOOT.md (restart, restore backup, etc.)
  • Bug reports include logs (customer must paste /v1/health output)
  • GitHub issue template guides them to solution before opening issue

Risk: Datacenter goes down (for SaaS phase 6)

What could go wrong?

Will's SaaS is down. All customers' auth fails.

Mitigation (phase 6+)
  • Multi-region Postgres (replicas in different AZ)
  • Automated failover (RTO <5 minutes)
  • Status page (status.n0passtemps.io, automated checks)
  • SLA in Pro tier only (99.5%), Free tier is best-effort
  • Customers can always fall back to on-premise (no lock-in)

Risk: Security vulnerability discovered (in WebAuthn lib or Go crypto)

What could go wrong?

CVE in go-webauthn or golang.org/x/crypto. n0passtemps is affected.

Mitigation
  • Dependabot enabled (automated dependency updates)
  • Security advisories monitored (Go security mailing list)
  • Patch release process documented (can ship hotfix in 2 hours)
  • Customers on latest version auto-get updates (in SaaS)
  • On-premise customers get release notes + upgrade instructions

Risk: "My keys/passwords are not encrypting properly"

What could go wrong?

Customer misconfigures KEK, loses it, can't decrypt secrets.

Mitigation
  • KEK backup prompted at init (BACKUP YOUR KEK FILE)
  • KEK versioning means old keys still decrypted (can rotate slowly)
  • GDPR right-to-delete doesn't require KEK (mark credentials revoked, purge after 30 days)
  • Recovery: force re-enrollment (users log in with recovery codes, enroll new credential)
  • Documentation: "What if I lose my KEK?" (step-by-step recovery)

Risk: Admin abuse (rogue admin revokes all users)

What could go wrong?

Disgruntled sysadmin revokes all credentials via admin API.

Mitigation (v1 Complet)
  • Dual-approval queue (sensitive ops require 2 admins)
  • Immutable audit log (proof of what happened)
  • Revoked credentials can be un-revoked within 24h by another admin
  • Alert on bulk revocation (>10 users in 1 hour)

Risk: Performance degradation (database slow)

What could go wrong?

Audit log grows, queries slow down. Auth latency >100ms (bad UX).

Mitigation
  • DB indexes on tenant_id, subject_id, created_at (queries fast)
  • Audit log pagination (no big queries)
  • Postgres for Complet (better query planner, replication for read scaling)
  • Monitoring recommendations (check slow query log, add indexes if needed)
  • Documentation: "Tuning database performance" (MONITOR.md)

Risk: Compliance change (GDPR, French law update)

What could go wrong?

New regulation requires different data retention. n0passtemps doesn't support it.

Mitigation
  • Architecture designed for compliance (audit log immutability, GDPR delete, retention policies)
  • On-premise customers can customize (it's open-source, MIT licensed)
  • Will can add features if multiple customers need it
  • SaaS customers get updates automatically (no choice)
